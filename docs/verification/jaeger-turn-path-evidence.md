## Findings

### Finding 1 — a refusing bridge is reported as a model-configuration problem

**Status: open.** `integrations/providers/jaeger/active_model.py` and
`status.py` are unmodified at the commit above.

`active_model()` wraps the `serving_model` bridge query in
`except Exception: logger.debug(...)` and returns an all-`None` dict. `status.py`
then takes its `if not model:` branch. The operator is told to check their model
configuration for a fault no model change can fix, and the actual cause is
written only to a debug log.

`status.py` has a dedicated branch for this failure that carries the exception
text — `"...its bridge is not answering"`, `reason=f"...: {exc}"`. That branch is
unreachable for any error `active_model()` catches, which is all of them.

The module comment states the intent that the code does not implement:

> The bridge query is therefore the probe, and its failure is the status — not a
> swallowed detail that degrades the message to a shorter sentence.

Observed, same process, seconds apart:

Both blocks below come from a single run of the probe script, seconds apart in
one process:

```
Reported status — what the operator is told
  available : True
  state     : needs_attention
  message   : JaegerAI is installed at /Users/matthewjenkins/GitHub/JaegerAI but reports no serving model.
  details   : {"reason": "The bridge answered without naming a model, so no runtime is serving turns.",
               "fix": "Check the selected instance's model configuration."}

Bridge queries — what the runtime actually answers
  serving_model : JaegerError: a bridge is already running for this instance
                  (pid 76424, .../.jaeger_ai/instances/ares/run/jaeger.pid)
  model_catalog : JaegerError: a bridge is already running for this instance (...)
  contract      : JaegerError: a bridge is already running for this instance (...)
  list_tools    : JaegerError: a bridge is already running for this instance (...)
```

The bridge did not answer. It refused, with a specific and actionable reason,
and the status text asserts the opposite.

Pinned by `test_status_names_the_bridge_failure_instead_of_blaming_the_model`
(`xfail(strict=True)`) in
`services/controller/tests/test_jaeger_attach_and_status_honesty.py`.

The same swallow reaches further than the status panel. `JaegerBackend.tools()`
converts any exception to `[]`, so on this machine ARES reports a runtime with
zero tools rather than one it could not interrogate. A model told it has no
tools will not call one, which makes this a behaviour change and not a display
bug. Pinned by
`test_an_unreadable_tool_list_is_distinguishable_from_an_empty_one`
(`xfail(strict=True)`).

Not a finding: `available: True` alongside `NEEDS_ATTENTION` is deliberate and
documented on `ProviderStatus.available` — a provider that answers should not be
refused dispatch.

### Finding 2 — the attach socket never matches the instance Jaeger serves

**Status: open.** Root cause is in JaegerAI, mirrored faithfully by ARES.

`bridge_socket.candidate_paths()` substitutes the literal `"default"` for an
unset instance. `instance.default_instance_name()` resolves an unset instance as
`JAEGER_INSTANCE_NAME` → the `active_instance` sticky file → `"default"`.
`candidate_paths` implements the first and last steps and skips the middle one —
the only step that differs once anyone has run `jaeger agent use <name>`.

This defeats the mechanism the socket exists for. From `bridge_socket`'s own
module docstring:

> Stdio is 1:1. The instance lock is 1:1. Together they made ARES and
> JaegerAI.app fight. This socket is the attach point: the process that holds the
> lock listens here, and every other client connects instead of spawning a second
> `jaeger bridge`.

A client that looks under the wrong instance does not just miss the attach — it
falls through to spawning, and that spawn collides with the very lock the socket
was added to route around. That collision is the `JaegerError` in Finding 1.

```
Attach candidates — where ARES looks vs. where the bridge listens
  ARES explicit selector : None
  Jaeger sticky default  : 'ares'
  candidates ARES will try:
      exists=True  .../.jaeger_ai/instances/default/run/bridge.sock
      exists=False ~/.jaeger/instances/default/run/bridge.sock
  sockets on disk, and whether anything is listening:
      LISTENING                    .../.jaeger_ai/instances/ares/run/bridge.sock
      stale (Connection refused)   .../.jaeger_ai/instances/default/run/bridge.sock
      stale (Connection refused)   .../.jaeger_ai/instances/jarvis/run/bridge.sock
```

ARES offers exactly one existing candidate, and it is a stale file. The live
listener is under `ares` and is never in the candidate list.

Pinned in both repos:
`test_candidate_paths_follow_the_sticky_default_instance` (JaegerAI, root cause)
and `test_attach_candidates_follow_the_sticky_default_instance` (ARES, mirror) —
both `xfail(strict=True)`.

### Finding 3 — `is_gateway=False` for the one runtime that owns its transcript

**Status: fixed in the working tree by concurrent work, not by this pass.**

At commit `5cac53b96`, `JaegerBackend.get_worker_target()` returned
`(run_jaeger_streaming, False, True)`. Verified by running the real router:

```
Backend selection — the flag chat_runtime actually branches on
  class        : api.providers.jaeger.backend.JaegerBackend
  defined in   : .../integrations/providers/jaeger/backend.py
  worker target: api.providers.jaeger.streaming.run_jaeger_streaming
  is_gateway   : False   <- selects the prompt shape
  is_jaeger    : True
```

Re-running the same probe against the current working tree prints
`is_gateway : True`.

`chat_runtime.py` branches on that flag: gateway workers get the clean user turn,
everyone else gets `build_context_prompt(...)`. So ARES serialized a transcript
for the single runtime it records as `transcript_owner="jaeger"` and hands a
session id to over the bridge — the runtime that already has those turns.

The uncommitted working tree now returns `True`. The pinning test lives in
`test_jaeger_production_promises.py` (concurrent work).

Consequence worth knowing, not a defect: the `[ARES runtime context]` block is
built only inside `build_context_prompt`, so under the gateway shape it no longer
reaches Jaeger. The selected model and provider still reach the worker as
`model` / `model_provider` arguments, and Jaeger selects its own serving model,
so nothing the runtime needs was lost — only prompt text telling a runtime its
own identity.

### Finding 4 — `NameError` on the success path of every telemetry-bearing turn

**Status: fixed in the working tree by concurrent work, not by this pass.**

At commit `5cac53b96`, `streaming.py` assigned `STREAM_TURN_TELEMETRY[stream_id]`
on the success path of `_run_local_jaeger_turn` and read it in
`_merge_and_save_jaeger_turn`, but the name was never defined at module level or
imported. Confirmed by parsing the committed file's module-level bindings:

```
$ git show HEAD:integrations/providers/jaeger/streaming.py | python3 <ast scan>
STREAM_TURN_TELEMETRY defined at module level in HEAD: False
imported names containing STREAM: ['STREAMS', 'STREAMS_LOCK', 'STREAM_DELTA_TEXT',
  'STREAM_GOAL_RELATED', 'STREAM_LAST_EVENT_ID', 'STREAM_LIVE_TOOL_CALLS',
  'STREAM_PARTIAL_TEXT', 'STREAM_REASONING_TEXT']
```

The assignment sits inside the `try` whose `except Exception` evicts the bridge
client and returns an error string. A turn that generated an answer *and*
reported timing therefore discarded the answer, killed the live agent, and
surfaced a bridge error. This is exactly promise 4 — a successful request
producing a hidden exception — and it was invisible to a suite that never
asserted on the success path with telemetry present.

## Gaps — untested and mocked boundaries

These are the things this document does **not** establish.

1. **No real model turn ran.** The reference machine has no serving model, so
   nothing here proves generation, tool execution, or recall across turns. Every
   multi-turn assertion covers the prompt ARES *sends*, not what Jaeger *remembers*.
2. **The bridge subprocess boundary is mocked** in every eviction and hydration
   test. `_get_or_start_bridge_client` is stubbed; no real bridge was killed and
   restarted mid-session.
3. **No restart-between-turns run.** Turn-1-then-restart-then-turn-2 against a
   live server was not executed. The cold-start prompt shape is asserted from a
   reconstructed session object, not from a genuinely reloaded one.
4. **Persistence is verified by inspection, not round-trip.** That
   `Session.save()` writes `messages: []` for a jaeger-owned transcript is read
   from `api/models.py`, not proven by a save/load cycle.
5. **Provider timeout and reconnection are untested.** The 120-second
   `clarify` wait and the `_is_dead_bridge_error` retry have no timing coverage.
6. **`_run_local_jaeger_turn` retries exactly once** on a dead-bridge error. A
   bridge that dies on both attempts returns an error; that path is uncovered.
7. **Findings 3 and 4 were fixed by concurrent work in an uncommitted tree.**
   Neither fix has been run against a live model turn.

## Closing these gaps

The blocker for gaps 1–3 is a serving model, not test infrastructure. With one
configured, the sequence that would close them is: send turn 1 naming a fact,
send turn 2 asking for it back, restart the worker, send turn 3 asking again —
against the real server on the real port, asserting on the HTTP responses and on
a clean service log.

## Language rule

"Fully working", "production ready", "end-to-end complete", and "session
persistence works" are not claims this document will make. State what ran, at
which commit, and what it produced:

> Verified three-turn continuity against the real Jaeger backend at commit X.
> Verified recovery after worker restart. No exceptions appeared in the service logs.

An unverified promise is listed as unverified. A mocked boundary is named.
